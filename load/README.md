# Нагрузочное тестирование

Требование ТЗ (Middle+): архитектура должна выдерживать **1 000 000 сообщений и 100 000 пользователей в сутки**.

## Окружение

| | |
|---|---|
| Данные | 100 000 пользователей, **1 000 000 комментариев** (300 000 заглавных + 700 000 ответов) за 30 дней, случайные рейтинги |
| Бэкенд | окружение `load` (`back/.load.env`): порт 4200, БД `comments_load`, Redis DB 2, индекс Meilisearch `load_comments` |
| Запасной путь | второй экземпляр бэкенда на 4201 с недоступным Meilisearch, чтобы список читался из Postgres |
| Инструменты | [autocannon](https://github.com/mcollina/autocannon) (HTTP), свой Node-раннер (капча + POST, WebSocket), socket.io-client |
| Железо | **один ноутбук** (Apple Silicon): генератор нагрузки, бэкенд, Postgres, Redis и Meilisearch делят одни и те же ядра. Цифры занижены относительно отдельного сервера |
| Длительность | по 20 с на сценарий, 100 соединений (голоса — 50, запись — 25 параллельных пользователей) |

## Подготовка данных

| Шаг | Время |
|---|---|
| Postgres: 1M комментариев через `generate_series` (`seed.sql`) | ~37 с |
| Переиндексация 1M в Meilisearch: чтение Postgres keyset-батчами по 1000 и отправка | ~31 с |
| Индексация в Meilisearch до готовности | ~36 с |

## Результаты (`results.json`, 2026-10-26)

| Сценарий | RPS | p50 | p97.5 / p95 | p99 | Ошибки |
|---|---:|---:|---:|---:|---:|
| Чтение, страница 1 (Meilisearch) | **2 380** | 40 мс | 56 мс | 69 мс | 0 |
| Чтение, реалистичная смесь: 90% стр. 1–3, 9% стр. 4–50, 1% глубокие (Meilisearch) | **1 170** | 78 мс | 128 мс | 144 мс | 0 |
| Чтение, случайная страница 1…12 000 × случайная сортировка (Meilisearch) | 89 | 1 387 мс | 1 664 мс | 1 718 мс | 0 |
| Запись: капча + POST комментария, 25 одновременных пользователей | **470 комм./с** | 48 мс | 94 мс | 125 мс | 0 |
| Голоса: PUT like/dislike, 300 голосующих | **1 068** | 43 мс | 77 мс | 101 мс | 0 |
| WebSocket: 1 000 подключённых клиентов × 20 комментариев | доставлено **100%** | 19 мс | 31 мс | 39 мс | 0 |

Задержка WebSocket считается от отправки POST до получения события `comment_created` каждым из 1 000 клиентов.

### Запасной путь (Meilisearch недоступен) — найдено и исправлено узкое место

В первом прогоне чтение через Postgres давало 37 RPS при p50 2 с. План запроса показал, что тормозит не сама страница (1.5–5 мс по индексам), а `findAndCountAll`: подсчёт строился с джойнами `users`/`files` и занимал ~170 мс на каждый запрос. Количество заглавных от джойнов не зависит, поэтому подсчёт вынесен в отдельный `count` по частичному индексу (~28 мс).

| Запрос через Postgres, 1M строк | До | После |
|---|---:|---:|
| Страница 1, LIFO (одиночный запрос) | 217 мс | **16 мс** |
| Сортировка по User Name | — | 13 мс |
| Страница 50 | — | 12 мс |

Под полной нагрузкой исправленный запасной путь повторно не прогонялся, чтобы не нагружать машину. Ожидаемый рост — того же порядка (×6–13), так как раньше всё время уходило на подсчёт.

Там же нашлась проблема окружения: `could not resize shared memory segment … No space left on device`. Параллельным воркерам Postgres в Docker не хватает `/dev/shm` по умолчанию (64 МБ), поэтому в `docker-compose.yml` добавлен `shm_size: 256mb`.

## Выводы для 100 000 пользователей / 1 000 000 сообщений в сутки

- **Средняя нагрузка** — около 1–2 запросов/с (100 000 пользователей × ~10 действий / 86 400 с), **пик** при ×20 — 25–50 запросов/с.
- Чтение реалистичным трафиком держит **~1 170 RPS** при p99 < 150 мс, то есть запас **×20–40** над пиком даже на одном ноутбуке.
- Запись **~470 комментариев/с** — это 40 млн в сутки при требовании 1 млн.
- Голоса **~1 070/с**, WebSocket — 1 000 одновременных клиентов с p99 39 мс.
- **Слабое место — глубокая пагинация** (случайная страница из 12 000 с сортировкой): ~90 RPS, ~1.4 с. Meilisearch для больших `offset` с сортировкой перебирает до сотен тысяч документов. На реальном трафике это редкий случай (1% в смеси выше не испортил p99). Если понадобится — ограничить глубину (`maxTotalHits`), перейти на «бесконечную ленту» с курсором или кешировать глубокие страницы.

## Что заложено в архитектуру под этот объём

- **Чтение не нагружает Postgres:** список и сортировки идут из Meilisearch (read-model). Postgres — источник истины и запасной путь.
- **Одна выборка на ветку:** `root_uuid` позволяет достать все ответы страницы одним запросом, без рекурсивных CTE.
- **Индексы под каждый запрос:** частичный индекс заглавных по дате и по рейтингу, `(root_uuid, created_at)`, уникальный `(email, user_name)`.
- **Голоса:** денормализованные счётчики обновляются в той же транзакции с `SELECT … FOR UPDATE` по строке комментария. Под конкурентной нагрузкой счётчики не теряются (проверено e2e).
- **Переиндексация** идёт keyset-курсором по первичному ключу, без `OFFSET`: 1M документов за ~1 минуту.
- **Тяжёлая обработка файлов** (картинки, видео) вынесена в очередь Bull, HTTP-запросы её не ждут.
- **Масштабирование наружу:** бэкенд stateless, поэтому можно поднять несколько экземпляров за балансировщиком. Для WebSocket при нескольких экземплярах нужен `@socket.io/redis-adapter`, сейчас он не подключён. Лимиты `@nestjs/throttler` хранятся в памяти процесса, при нескольких экземплярах их нужно перевести в Redis.

## Как повторить

> Прогон заметно нагружает и греет ноутбук (до 100 соединений, 1 000 WebSocket-клиентов, миллион записей в Meilisearch займёт ~3 ГБ памяти).

```bash
docker compose up -d postgres redis meilisearch
cd load && npm install && npm run seed          # создаст БД comments_load
cd ../back && npm run build:e2e && npm run start:load   # создаст таблицы; оставить запущенным
cd ../load && npm run seed                      # 1M комментариев (~40 с) + очистка индекса
# перезапустить start:load — пустой индекс переиндексируется сам (~1 мин)
PORT=4201 MEILI_HOST=http://127.0.0.1:1 npm --prefix ../back run start:load   # запасной путь, в другом терминале
npm run run                    # все сценарии; или: node run.mjs read|fallback|write|votes|ws
```

После прогона освободить место:

```bash
curl -X DELETE -H "Authorization: Bearer $MEILI_MASTER_KEY" http://localhost:7702/indexes/load_comments
docker exec test-task-redis-1 redis-cli -n 2 FLUSHDB
docker exec test-task-postgres-1 psql -U comments -d postgres -c 'DROP DATABASE comments_load'
```
